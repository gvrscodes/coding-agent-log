# Agent Guidelines for Code Reviews and Explanations

This document defines the structure, tone, and conventions for files generated by agents into `docs/code-reviews` and `docs/explanations`.

---

## 1. Code Explanations (`docs/explanations/`)

### Purpose
To help the user clearly understand what the code does, how it works, and why specific design decisions or tradeoffs were made.

### File Naming Convention
- Format: `<kebab-case-topic-or-module>.md` or `YYYY-MM-DD-<topic>.md`
- Example: `path-traversal-validation.py.md`, `2026-10-14-root-navigation.md`

### Required Structure
1. **Title and Executive Summary**
   - High-level overview of what the module, feature, or change accomplishes in 2 to 3 sentences.
2. **What the Code Does**
   - Functional walkthrough of the component.
   - Core functions or classes, inputs, outputs, and side effects.
   - Flow diagram or step-by-step trace of execution when helpful.
3. **Why It Was Built This Way**
   - Rationale behind the architecture, data structures, or algorithm.
   - Tradeoffs evaluated and why alternatives were rejected.
   - Constraints considered (performance, security, simplicity, platform limits).
4. **Key Scenarios and Edge Cases**
   - How the code behaves under unusual conditions or errors.
   - Boundaries and limitations.

---

## 2. Code Reviews (`docs/code-reviews/`)

### Purpose
To provide objective, actionable feedback on code quality, correctness, security, performance, and adherence to project coding standards.

### File Naming Convention
- Format: `YYYY-MM-DD-<feature-or-pr-name>.md`
- Example: `2026-10-14-browse-api-review.md`

### Required Structure
1. **Review Summary**
   - Scope of review (files and commit range examined).
   - Overall assessment: pass, needs changes, or suggestions.
2. **Findings**
   - Categorize by severity:
     - **Critical / Blocker**: Bugs, security vulnerabilities, or breaking regressions.
     - **Improvement**: Code simplification, performance enhancements, edge-case coverage.
     - **Nitpick**: Naming clarity, minor comments, formatting.
   - For each finding: cite the file and line number, explain the issue, and provide a concrete proposed fix.
3. **Compliance Checklist**
   - Standards check (file size limits, function length, typing, error handling).
   - Test coverage status.

---

## 3. General Writing Standards

- **Tone**: Direct, technical, and objective. Focus on facts and reasoning.
- **Clarity**: Avoid jargon without explanation. Explain "why", not just "what".
- **Formatting**: Use standard GitHub-flavored Markdown. Use fenced code blocks with appropriate language tags for syntax highlighting.
- **Tone Rules**: Never use emojis. Keep text concise and actionable.
